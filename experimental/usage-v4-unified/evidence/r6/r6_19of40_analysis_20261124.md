## 2. Cause (consistent with code and numbers)
- Every start is serialised by ONE ScriptLock (`tryLock(20000)`) — required, because the dedupe check, append, commit read-back
  and commit watermark must be atomic.
- Work inside the lock per new start (mock profile, warm): TextFinder dedupe scan, `appendRow`, `flush`, read-back of the new row,
  watermark property write = **4 spreadsheet round trips + 1 property write** (cold first call: +2 manifest reads).
- Real hold: p50 **1006 ms**, p95 2283 ms. Capacity of one 20 s lock-wait window ≈ 20 000 / ~1 050 ≈ **19–20 starts**.
  Observed: 19 accepted, max successful lock wait **19 861 ms** (just under 20 000), the other 21 timed out waiting.
- `tryLock` fails BEFORE any write (Code.gs order: lock -> era check -> append), so a lock-timeout request leaves no row and is
  safe to re-send with the same eventId (idempotent: R6c, Node D/R7 tests).
- The earlier R6 run's 17 x 429 disappeared after the catalog cache (LIVE 7 / CACHE 12); 429 is not the current cause.
- Client-visible latency for accepted starts: rpc p50 22.9 s, max 24.8 s.

## 3. Minimal improvement options (not implemented in this step)
| option | effect | risk |
|---|---|---|
| A. keep the current design: server rejects cleanly, the game client re-sends the SAME eventId (inline retries + localStorage queue, today/yesterday horizon) | already shown: real R6b 40/40, mock D 40/40 under lock/429/lost-reply faults | a start is lost if the browser closes before any successful retry and is not reopened by the next KST day; failure is only in `status()` (no teacher-visible alert) |
| B. group commit: each start leaves an intent, the lock holder commits all pending intents with ONE dedupe read, ONE `setValues`, ONE flush, ONE read-back, ONE watermark write | server-only capacity scales with batch size instead of ~1/s | new write path; CacheService intents are lossy (owner must still self-commit); needs new mock tests + real isolated GAS run before any claim |
| C. raise `tryLock` | hides the limit, does not raise throughput; longer waits, more concurrent executions | **rejected** (40-6AO: do not just raise timeouts) |
Recommendation: A for now (no server change), plus the next real isolated run with per-request accounting (prepared in this step);
consider B only if the teacher needs > ~20 simultaneous starts per 20 s without relying on client retries.
