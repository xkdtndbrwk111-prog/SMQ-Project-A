## 2. 단일 GAS 아키텍처
**한 GAS 프로젝트 내 파일 분리 예시 (명칭은 설계상 제안):**
- `UsageV4Core`: 순수 집계·검증 로직 재사용
- `UsageV4Writer`: 기존 `recordUsageStartU1`와 append/멱등성/이벤트 ID 저장 책임
- `UsageV4Daily`: 일별 COMPLETE와 버킷 저장/재읽기·원본/요약 SHA-256 검증
- `UsageV4Reader`: 동일 프로젝트에서 인증된 과거 요약 + 오늘의 꼬리만 조회
- `UsageV4AdminAuth`: 관리자 권한 서버 측 검증 및 거부 우선
- `UsageV4AdminUI`: 관리자 전용 통계 화면 (홈/게임 bootstrap에서 통계를 자동 로드하지 말 것)
이름과 파일 개수는 변경 가능하지만 **모두 동일 GAS 프로젝트 내**에서 동작해야 한다.

**주의: 보안 설계 승인 게이트**
- `doGet()` 게임 엔드포인트가 익명 사용자에게 공개될 수 있으므로 같은 프로젝트의 `google.script.run` 호출 대상이 되는 관리자 RPC도 외부에서 호출 가능하다고 가정하라. 화면 숨김·클라이언트 플래그·URL 매개변수·하드코딩된 관리자 문자열/비밀번호로 관리자 권한을 대신하지 않는다.
- `Session.getActiveUser().getEmail()`은 익명 접근/배포 유형에 따라 비어 있거나 신뢰할 수 없으므로 **그 값만을 전제로 관리자 인증 PASS를 선언하지 말 것**.
- 실행 환경과 검증 가능한 Google 신원 증명, 토큰 발급/서버 측 검증·취소·만료·리플레이 방어, 관리자 허용 대상, 최소권한·감사로깅을 먼저 설계한다. 프런트엔드에 관리자 비밀/Script Properties/운영 시트 ID 노출 금지.
- 단일 GAS 프로젝트에서 **공개 게임과 비공개 관리자 통계를 안전하게 분리할 현실적인 인증 방법을 증명하지 못하면 구현을 HOLD하고 설계 대안을 제시**하라. 별도 Project B 복원으로 우회하지 않는다. 같은 프로젝트에서 여러 배포를 제안할 수 있으나, 배포 설정만으로 서버 측 인증을 대체했다고 가정하지 말 것.
- 사전 승인 없이 통계 RPC를 기존 익명 게임 UI에서 호출할 수 있도록 붙이지 말 것.

### 40-6-U1. Project A 단일 GAS 시험 코드로 통합
- 기존 V4 CORE, 단일 Writer/Reader/일별 집계/승인 관리자 게이트를 **독립 시험 GAS**에 연결. Project B의 `requireUsageStatisticsAccessU3_`는 신규 시스템의 의존성이 아님.

- 저장/조회가 동일 `LockService.getScriptLock()`과 합의된 append/commit-watermark 정책을 지키는지 설계·모의 검증. 안정된 읽기 절단점 없이는 PASS 금지.
