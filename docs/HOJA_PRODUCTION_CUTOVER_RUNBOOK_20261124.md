# HOJA 1.5 — 신규 문제은행 운영 연결 절차서 (40-6BM, 2026-11-24)

**공식 게임명: HOJA 1.5.** 저장소명은 `SMQ-Project-A`로 유지하며, 이 문서의 과거 'HOJA 2.0' 표기는 1.5의 운영 대상 식별 과정에서 나온 구표현이다. 별도로 개발 중인 HOJA 2.0과 다른 프로젝트다.

**상태: 준비 문서. 운영 GAS·시트·랭킹·배포는 아직 아무것도 바꾸지 않았다.**
아래 "확인 필요 3가지"가 답해지면 그대로 실행한다. 원칙은 다음과 같다.
- 기존 운영 게임·학생 기록·랭킹을 보존한다.
- 격리 사본 전용 설정을 운영에 옮기지 않는다.
- 언제든 1분 안에 되돌릴 수 있어야 한다.

## 0. 확인 필요 3가지 (교사)
1. **운영 프로젝트가 어느 것인가.**
   - `clasp list`의 "SUPER MARIO QUIZ…"를 읽기 전용으로 확인했더니 HOJA 2.0 구성이 아니었다(Code.js 627 KB, Feedback·Supabase, Index/Script/Styles). 받은 사본은 즉시 삭제했다.
   - HOJA 2.0 운영 프로젝트(`Code.gs` + `Game.html` + `UsageRollupU3S.gs`)의 **편집기 이름이나 주소**가 필요하다. 이 계정의 다른 프로젝트 이름에도 해당하는 것이 보이지 않는다.
2. **전환하면 게임 목록이 신규 23단원으로 바뀐다.**
   - 운영 빌드는 승인 단원이 활성화되면 공개 목록을 **승인 23단원만** 보여준다. 기존 시트(Project B) 카트리지는 목록에서 빠진다(시트와 기록은 그대로 보존).
   - 그대로 진행해도 되는가.
3. **전환 순간에 `HOJA_USAGE_APPROVED_ERA_START`를 설정해야 한다.**
   - 운영 빌드는 이 값이 없으면 승인 목록 자체를 거부한다(`APPROVED_ACTIVE_BEFORE_ERA_START`). 즉 "통계는 정식 배포 때 연결"이 이 순간이다.
   - 값은 전환일(예: 전환 당일 KST 날짜)로 한다. 그날 이전 기록은 기존(legacy) 집계로 남는다.

## 1. 운영 빌드 준비 (저장소만, 운영 무변경)
- `approved-catalog/deployment/active-deployment.json`에 23단원을 기록한다. 항목마다 다음을 넣는다.
  - `teacherDeploymentApproval: APPROVED`, `approvedOn`
  - 정확한 `effectiveSha256`
  - `rendererGate: PASS`, `questionValidationGate: PASS`(근거: F3-3 렌더 732×4, 40-6BF/BK 실플레이)
  - `mediaRightsAcknowledged: true`(교사 결정 40-6AZ)
- `build_active_catalog.mjs`에 `--content-commit`을 추가한다. 카탈로그는 `GITHUB_RAW_PINNED_V1 @ 440cc1f`(공개 게시본, 23/23 SHA 일치)를 쓰고, 내장 콘텐츠는 0개로 한다.
- 안전장치를 갱신한다. 지금은 "커밋된 운영 빌드 = 활성 0개"로 강제하고 있다. 이를 "활성 항목이 있으면 반드시 고정 commit 원격 소스와 내장 콘텐츠 0개"로 바꾼다(`UNIFIED_GAS_F1` 시험, `verify_release_candidate.py`).
- 운영 번들은 다음으로 구성한다(크기 약 8.77 MB, 격리 프로젝트 저장 성공 크기).
  - 통합 release 8파일
  - 운영의 `UsageRollupU3S.gs`(그대로 유지: 매일 00:15 집계 트리거가 참조)
  - 운영의 `appsscript.json`
- 전역 이름 충돌 검사: 통합 5개 .gs와 `UsageRollupU3S.gs` 사이에 중복 0, 한 전역으로 합친 문법 검사 OK(40-6BM).
- 운영 설정에서의 동작(코드 근거):
  - 격리 속성(`HOJA_V4_UNIFIED_ISOLATION`)이 없으면 V4 copy-only 경로는 꺼지고, 사용량은 기존 U1 방식으로 운영 `EVENT_LOG`에 기록된다.
  - 루트 `Code.gs`의 opt-in 가드는 속성이 없으면 동작이 같다.
  - 랭킹은 `HOJA_PROD_RANKING_SPREADSHEET_ID`를 그대로 쓰고, 새 단원 ID로 새 랭킹판이 생긴다. 기존 랭킹은 보존된다.
- mock 검증: 운영형 속성(격리 속성 없음, 시작일 설정)에서 LIST 23, GET, 시작 기록 1행을 확인한다. 기존 시험은 반복하지 않는다.

## 2. 백업 (전환 직전, 읽기 전용)
1. `clasp pull`로 운영 프로젝트 전체 파일을 받는다. 로컬 보관만 하고 커밋하지 않는다.
2. 운영 웹앱 **현재 배포 버전 번호**를 기록한다(배포 관리 화면). 되돌리기의 핵심이다.
3. 스크립트 속성 **이름 목록**과 트리거 목록을 기록한다(교사가 편집기에서 확인, 값은 적지 않음).

## 3. 전환 (수업 없는 시간)
1. Claude: 운영 프로젝트에 운영 번들을 `clasp push`한다. HEAD만 바뀌고 학생용 배포 주소는 아직 이전 버전이다.
2. 교사: 프로젝트 설정 → 스크립트 속성에 `HOJA_USAGE_APPROVED_ERA_START = 전환일`을 추가한다.
3. 교사: 배포 → 배포 관리 → 운영 웹앱 연필 → 버전 "새 버전" → 배포. 주소는 그대로다.
4. Claude: 운영 주소에서 대표 확인만 한다.
   - 싱글: 시작 → 문제 입력 → 결과
   - 팀전: 시작 → 진행
   - 아케이드: 시작
   - 통계 화면 열림
   - 익명 운영자 함수 거부

## 4. 되돌리기 (문제 발생 시, 1분)
1. 교사: 배포 관리 → 운영 웹앱 연필 → 버전을 **2-2에서 기록한 이전 번호**로 → 배포. 주소는 그대로이고 즉시 이전 게임으로 돌아간다.
2. 교사: `HOJA_USAGE_APPROVED_ERA_START` 속성을 삭제한다.
3. Claude: 백업 파일을 HEAD에 다시 push한다. 매일 집계 트리거가 HEAD 코드를 실행하므로 필요하다. 이후 `clasp pull`로 대조한다.
4. 데이터: 전환 동안 쌓인 신규 단원 시작 기록은 `EVENT_LOG`에 append-only로 남는다. 삭제하지 않는다.

## 5. 하지 않는 것
- 격리 사본 전용 속성/시트/토큰을 운영에 넣지 않는다.
- 실제 Seal·자동 마감 트리거를 설치하지 않는다(후속).
- 기존 기록 삭제나 재작성을 하지 않는다.
- 물속 충돌과 movement-smoke 조사는 하지 않는다(교사 중단 지시).


## 6. GPT-6 검수 보완 — 운영 전환 전 필수 확인을 한 가지로 축소 (40-6BN, 2026-11-24)
**주의:** 본 문서는 `SMQ-Project-A` 기존 게임의 신규 문제은행 연결용이며, 별도 개발 중인 **HOJA Game 2.0** 프로젝트와 혼동하지 말 것. 40-6BM에서 'HOJA 2.0 운영 프로젝트'라고 칭한 표현은 실제 프로젝트 식별 근거가 아니다.
- **운영 GAS 프로젝트는 여전히 미확인(유일한 외부 선결조건).** 과거 대화에서 'SUPER MARIO QUIZ(Project A)'라는 명칭이 사용됐으나, 최근 같은/비슷한 이름의 파일을 pull하니 다른 프로그램(Feedback/Supabase 등)이었다. **이름만으로 고르거나 다른 앱에 push 절대 금지.** 현재 학생이 사용하는 게임의 기존 편집기 URL 또는 배포 주소를 교사에게 한 가지만 요청하고, 확인한 뒤 계정·코드·파일 구성·기존 배포를 상호 대조한다.
- **새 23단원 연결은 기승인. 하지만 기존 76개 카트리지를 목록에서 완전히 숨기는 것은 독립적인 UX/운영 정책 변경이다.** 확인 없이는 '23개만 교체'를 운영에 적용하지 말고 기존 게임/주소와 기존 목록이 유지되도록 별도 시험·운영 배포 준비 후 전환 정책을 보고한다. 서버가 공개 목록 두 집합을 동시에 제공하지 못하면 그 사실과 최소 변경 대안을 먼저 명시한다.
- **통계:** 교사 결정은 정식 출시와 동시에 집계 시작일 설정, 그전까지 미설정이다. 현재 구현은 `HOJA_USAGE_APPROVED_ERA_START` 없이는 RELEASE approved catalog 자체를 차단하므로, **운영 배포 순간** 설정하는 것이 필수. 통계의 경미한 혼재·누락은 후순위지만 학생 플레이 실패/서버 데이터 손상은 차단.
- **롤백 시간:** 이전 버전 선택은 빠른 사용자 화면 복구 단계일 뿐 **전체 원상복구 1분 보장 아님**. HEAD를 사용하는 시간 기반 트리거 `UsageRollupU3S.gs`, 스크립트 속성, 사용량 기록은 별도 보존/복원이 필요하다. `clasp pull`로 실제 운영 프로젝트의 전체 파일·manifest 및 트리거 함수명을 식별한 뒤, 임시 변경→복구 절차를 한 번 수동으로 검토.
- **권리 필드:** `mediaRightsAcknowledged: true`는 공개 게시를 진행하라는 교사 지시의 확인에 불과하며 제3자 자료의 재배포 권리를 **입증하지 않는다**. 적법한 이용 근거가 확인되지 않은 이미지를 '권리 해결 완료'로 표시하거나 출처 미확인 자료를 추가 게시하지 말 것.
- **검증 최소화:** 올바른 운영 프로젝트 확인 후 작업은 백업→최소 통합→새 배포→**시작·문제 응답·종료 대표 1회 및 권한/데이터 치명 오류만** 확인. 이미 통과한 전체 23단원/40건 부하/25풍선/팀전 전수 재시험 금지.

## 8. 최소 변경 대안 확정 + GitHub 내부 운영 빌드 준비 (40-6BP, 2026-11-24)
**사실:** 현재 서버는 승인 단원이 활성화되면 공개 목록에 승인 23개만 낸다(기존 76개와 동시 제공 불가). 서버를 고쳐 두 목록을 섞는 것은 이름 충돌·사용량 시대 규칙까지 바꾸는 큰 변경이라 택하지 않는다.
**최소 변경 대안(권장): 같은 운영 프로젝트에 배포 두 개.**
- 기존 학생용 주소: **이전 버전에 그대로 고정**한다. 기존 76개, 기록, 랭킹을 그대로 유지한다.
- **새 HOJA 1.5 주소:** 새 버전(신규 23단원). 교사가 필요한 반에만 안내하고, 나중에 기존 주소를 옮길지는 별도로 결정한다.
- 코드 근거:
  - ① 기존 버전 서버는 시작일 속성을 읽지 않는다(`HOJA_USAGE_APPROVED_ERA_START` 참조 0).
  - ② 00:15 집계(`UsageRollupU3S.gs`)는 다른 파일에 의존하지 않는다. 새 A1 행은 단원별 집계에서 빠질 뿐 오류가 아니다(숫자 ID만 단원 집계).
  - ③ 새 배포에서 기존 시트 단원 시작은 기록을 거부한다(`USAGE_LEGACY_CATALOG_RETIRED`). 그래서 기존 76개는 기존 주소에 두는 것이 맞다.
- 주의: HEAD push는 시간 트리거 코드(집계)를 바꾼다. 집계 파일은 원본 그대로 포함하고, 백업에서 트리거 함수명을 대조한다.

**GitHub 내부 준비 완료(운영 무변경):**
- `build_active_catalog.mjs --content-commit`: 고정 원격 RELEASE 목록을 생성한다. 옵션이 없으면 기존과 동일하고, 커밋된 활성 목록은 0개를 유지한다.
- `approved-catalog/deployment/hoja15-production-draft.json`: 23단원 배포 **초안**이다. 커밋된 `active-deployment.json`은 0개 그대로다. 매체 권리 확인 ≠ 권리 해결.
- `assemble_hoja15_production.py`: 운영 번들(통합 release + 운영 집계 + 운영 manifest)을 저장소 밖에 만들고 검증한다. 결과는 **PASS**(8,779,489 B, 활성 23, `440cc1f` 고정, RC 감사 PASS, 전역 중복 0). 근거 `evidence/bp/`.
- mock(운영형 속성)
  - 시작일이 없으면 목록을 거부한다.
  - 시작일을 넣으면 23단원 목록과 A1 시작 1행이 나온다.
  - V4는 꺼져 있고, 익명 운영자 함수는 거부한다.
  - **알려진 한계:** 운영 U1 경로는 같은 이벤트 ID 재전송을 중복 기록한다(기존 운영도 동일). 후순위 통계 과제다.

**남은 선결조건: 운영 GAS 프로젝트 식별 1가지**(현재 학생이 쓰는 게임의 편집기 링크나 /exec 주소). 식별되면 다음 순서로 진행한다.
1. 백업: pull, 현재 배포 버전 번호, 트리거·속성 이름.
2. 번들 push(HEAD).
3. 시작일 설정.
4. **새 배포 생성**(기존 배포는 건드리지 않음).
5. 대표 플레이 1회.

1. Claude 보고 완료: 학생용 실제 기존 deployment **@406**가 맞는 운영 GAS를 찾아 HEAD에 신규 HOJA 1.5 번들 업로드(재확인 9/9), 이전 버전 코드와 사용량 트리거 보존; 이 단계의 불필요한 전수 시험·재백업 금지.
2. 교사: 운영 GAS 스크립트 속성 `HOJA_USAGE_APPROVED_ERA_START`를 **실제 KST 출시일**(11/24 야간 출시라면 `2026-11-24`)로 추가/확인. 승인 목록 실행의 필수 조건.
3. 교사: **배포 → 배포 관리 → 현재 학생용 기존 @406 deployment(실제 URL과 ID 일치 확인) → 수정(연필) → 버전 '새 버전' → 배포.** `새 배포`를 클릭하지 말 것. 학생용 URL이 바뀌지 않으며 실제 새 버전 번호는 결과에서 확인한다.
4. 새 기존 URL에서 **HOJA 1.5 목록 23단원 표시 및 대표 시작→문제 입력/진행→종료 한 번** 확인. 기존 원격 76단원은 새 게임 메뉴에서 보이지 않지만 **원본 시트·기존 이용 기록·랭킹은 삭제되지 않는다**.
5. 문제 발생 시 **동일 기존 deployment에서 @406으로 버전 재선택**해 화면을 되돌리고, Script Properties/HEAD 트리거 영향이 있다면 필요에 따라 시작일 속성 및 보존 HEAD까지 되돌린다. 화면 버전 복원과 백엔드 전체 복원이 같은 작업은 아니다.

**최신 정책 우선순위:** 본 §9 및 중앙 체크리스트 40-6BV가 최종. 별도 두 배포 운영, 기존 @406 절대 수정 금지, `새 배포` 생성 안내는 **이전 정책으로 폐기**. 운영 학생용 배포 이외의 @384/@368 및 격리 @9는 수정하지 않는다.
