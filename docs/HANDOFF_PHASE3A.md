# HOJA QUIZ Phase 3A — 학급 대결 설계안 / 감독 검토용

기준 `6599022fc2d5844241b60d692782c12c4289a3ea`. 이 문서와 시험 시나리오는 **제안**이다. 학급 대결, Firebase 연결, 인증, 점수 제출 또는 UI를 구현하거나 실제 프로젝트에 배포한 결과가 아니다. 이 설계의 규칙·숫자·데이터 형식은 감독 검토 후 확정한다. Phase 2D 정본과 Phase 1·2 기준 기록을 보존한다.

## 제안 구조와 신뢰 경계

```text
교사 화면 ── 인증된 세션 생성·관리 요청 ──┐
학생 학급 진입 ── 입장·재접속 요청 ──────┼── 신뢰 가능한 세션 서비스 ── 격리된 데이터 저장소
      │                                  │       └─ 권한·전이·중복·종료 판정
      └─ 기존 엔진 iframe ← 검증된 카트리지·설정
             └─ 최초 결과를 class 어댑터가 부모에 전달 → 서비스에 제출
싱글 교사/학생 경로 → 기존 오프라인 서비스와 엔진만 사용 (Firebase 0건)
```

단일 엔진을 공유하고 모드별 진입·서비스 어댑터만 분기하는 안이다. 학급 기능 로드는 class 경로에서만 명시적으로 선택한다. 새 메시지는 별도 이름·버전·필수 필드를 쓰고 `event.source`와 허용 origin, 세션·실행 ID를 검증한다. 기존 `postMessage('*')`의 호환 경로에 인증 비밀을 실어 보내지 않는다. 게임 실행 버전과 카트리지 ID·콘텐츠 해시를 세션에서 고정하고 진입 전에 대조한다. 다른 버전일 때 새 QR 안내; 무조건 캐시를 신뢰하지 않는다.

교사가 동일 시드로 맵을 제공할지, 학생별 시드를 쓸지, 문항·보기 순서까지 같게 할지는 공정성 결정이 필요하다. 동일 시드만의 동등성은 주장하지 않는다. 맵 생성·문제 선택·애니메이션에 섞여 쓰이는 난수와 시계, 실제 질문/보기 순서를 조사하고 기존 엔진을 바꾸지 않는 범위에서 시나리오를 검증해야 한다. 서로 다른 학생별 진행이 동기화되는 멀티플레이나 위치 공유는 현재 범위에 포함하지 않는다.

## 세션·참가·재접속 제안

세션 상태(서버가 단조 증가 `revision`과 함께 변경):

```text
DRAFT → LOBBY → RUNNING → CLOSING → FINALIZED
              ↘ CANCELLED          ↘ CANCELLED (교사 사유 기록)
```

- `DRAFT`: 교사와 게임/카트리지 버전·세션 설정 준비. `LOBBY`: 입장, 중복 확인, 팀 배정·준비 상태 표시. 시작 시 멤버·팀 구성을 동결하는 방안을 제안한다. 동결과 입장 요청의 경합은 같은 트랜잭션의 직렬 순서로 수용/거부한다.
- `RUNNING`: 서버의 시작 이벤트를 받아 각 학생이 기존 엔진에서 독립 실행한다. 시작 동시성의 지연은 측정·표시해야 하며 완전한 동시 시작을 보장하지 않는다. 개인별 600초는 기존 일시정지 규칙 그대로다.
- 종료 조건은 **교사가 종료를 확정할 때** `CLOSING`을 커밋하는 안을 제안한다. 남은 학생의 기존 로컬 게임을 강제로 종료하거나 600초를 바꾸지 않으며, 세션 결과 수락이 중단됨을 안내하는 동작은 별도 설계한다. 그 전까지의 수락 결과와 미제출/연결 끊김을 표시하고 교사에게 영향을 보여 준다. `CLOSING` 이후 새 제출은 거부하고 한 번만 집계해 `FINALIZED`로 고정한다. 타임아웃, 최대 수업 시간, 종료 대기·유예 시간과 사전 공지는 별도 제품 결정이다. 이 제안은 세션 벽시계와 개인 게임 시계를 혼동하지 않는다.
- 학생 식별은 서버가 발급한 임의 `participantId`와 인증 UID의 멤버십으로 한다. 표시 이름은 식별자가 아니다. 같은 UID·같은 입장 요청의 재시도는 같은 참가자를 반환하고, 다른 UID가 같은 이름을 내면 자동 병합하지 않고 교사 판단/거부 정책을 적용한다. 기기·브라우저가 같다는 것만으로 다른 학생을 동일인으로 판정하지 않는다.
- 팀 배정은 교사 권한이며 동결 후 임의 변경하지 않는다. 팀별 합계/평균·결원 처리·동점 규칙은 미확정이다. 확정 전 저장소의 기계적 합산은 시제품 정보로만 취급한다.
- 같은 탭이 살아 있는 일시적 단절은 게임 로컬 상태를 리셋하지 않고 같은 인증·실행 ID로 연결만 재개한다. 서비스는 `connectionEpoch`를 증가시키며 이전 탭의 낡은 epoch 요청을 거부한다. 네트워크의 연결 표시와 실제 게임 실행 상태는 구분한다.
- 페이지 새로고침, 브라우저 종료, 기기 변경으로 Scene이 사라지면 **현재 엔진에서 중간 상태를 복원할 수 없다**. 이름이나 이전 점수를 입력해 자동 복원하지 않는다. 교사가 제외/새 실행/보류 중 결정하는 예외 절차를 제안하며, 새 실행의 공정성·제출 자격은 감독 결정 전 미확정이다. Firebase 익명 인증은 저장소 삭제·기기 변경 시 동일 UID 유지를 보장하지 않는다. 인증 상실 시 교사 승인된 새 기기 연결 절차가 필요하다.
- 오프라인 결과는 확인 전 `제출 대기`일 뿐 확정 점수가 아니다. 기존 요청 ID·내용으로 재전송하고 서버 응답 확인 뒤 확정한다. 종료 후 도착한 결과를 단말 시계로 소급 처리하지 않는다. 수동 예외나 재개방은 별도 감사와 정책 승인 없이는 하지 않는다.

## 저장·인증·권한 제안

1. **환경**: 로컬 Firebase Emulator Suite는 프로젝트 ID `demo-hoja-phase3a`만 사용한다. 분리 시험 클라우드는 향후 별도의 비운영 프로젝트·계정·규칙·예산·자격증명으로만 구성하며, 아직 생성하지 않는다. 운영 프로젝트 ID·키·서비스 계정·GAS/Sheets를 개발판과 공유하지 않는다. Emulator가 하나라도 빠지면 시작 실패하며 실제 서비스로 대체하지 않는다. [Firebase 공식 문서](https://firebase.google.com/docs/emulator-suite/connect_firestore)는 `demo-` 프로젝트에서 에뮬레이트되지 않은 리소스에 대한 호출이 실패한다고 설명한다.
2. **인증**: 교사는 검증된 교사 계정과 서버 측 세션 소유권을 사용한다. 학생은 계정 없는 기기에서 임시 익명 인증과 세션 전용 참가 자격을 결합하는 안이다. 익명 UID 자체는 학생 본인·교사 역할의 증명이 아니다. 교사 권한은 클라이언트가 정한 필드로 부여하지 않는다. 복구·교사 소유권 위임·학교 계정 사용 가능성은 승인 전 결정한다. [인증 상태 지속](https://firebase.google.com/docs/auth/web/auth-state-persistence)은 기기·브라우저 저장 상태에 의존한다.
3. **QR·입장**: 싱글 QR과 별도 class 진입점/모드를 사용한다. 세션 공개 식별자만으로 권한을 주지 않고, 교사가 발급한 고엔트로피·짧은 만료의 입장 자격을 서버가 검증·폐기하고 요청 제한을 건다. 자격은 URL 쿼리·로그·분석에 남기지 않는 전달 방식을 구현 전 검토한다. QR 복제 가능성을 인정하며 학급 밖 입장 방지·교사의 참가 승인 필요 여부는 별도 결정이다.
4. **자료 모델 초안**: `sessions/{sid}`에 소유자·상태·revision·고정 게임/카트리지 버전·시작/종료 서버 기록, `sessions/{sid}/participants/{pid}`에 UID 연결·표시명·팀·연결 epoch·참가 상태, `.../runs/{runId}`에 실행 소유자·실행 상태·최초 결과 해시·수락 영수증, `.../teams/{teamId}`에 배정과 공개 집계, 별도 비공개 경로에 필요한 최소 응답 자료. 민감한 정답·다른 학생의 개별 응답은 학생에게 공개하지 않는다. 실제 보존 기간·삭제·접근 권한·분석 목적은 교사와 감독 검토 전 미확정이며 기본은 최소 수집·세션별 삭제를 제안한다.
5. **권한**: 기본 거부. 클라이언트의 역할 변경·다른 학생 응답 읽기·팀 배정·집계·점수/종료 상태 직접 쓰기를 금지한다. 교사 명령과 입장·결과 수락은 인증 검증과 서버 트랜잭션을 거치는 신뢰 서비스만 처리한다. Firestore 클라이언트 읽기도 소유자/멤버십·필드 공개 범위별로 Rules에서 제한한다. 서버 SDK는 Rules를 우회하므로 서버 IAM과 요청 인증을 별도로 통제해야 한다. [Firestore Rules 문서](https://firebase.google.com/docs/firestore/security/rules-conditions).
6. **시험 환경의 현재 상태**: `verification/phase3a/emulator/`에는 loopback·demo 프로젝트용 설정과 모든 읽기·쓰기를 막는 기본 규칙만 있다. Rules나 클라우드 함수를 구현한 것이 아니다. 연결 대상 검증과 기본 차단 계획을 먼저 검토한다. 공식 문서에 따르면 Rules 설정이 없으면 에뮬레이터가 열린 규칙으로 동작할 수 있으므로, 규칙 파일을 명시하고 누락 시 시험을 중단한다. [에뮬레이터 Rules 시험](https://firebase.google.com/docs/firestore/security/test-rules-emulator).

## 중복 제출과 종료 경합

- 서버는 세션·참가자·실행 소유권, 고정 버전, 현재 상태·connectionEpoch, 필드 타입·범위와 최초 제출 여부를 검증한다. `runId`는 서버가 발급하고 한 참가자의 한 실행에 귀속한다. 요청 ID는 생성 후 재시도에도 유지한다.
- 동일 `(sid, pid, runId, requestId)`와 같은 정규화된 payload 해시의 재전송은 이전 영수증을 돌려준다. 같은 ID에 다른 내용은 충돌로 거부하고 최초 기록을 보존한다. 다른 ID라도 이미 확정된 `runId`의 두 번째 결과는 집계하지 않는다. 점수 저장·집계 반영 또는 집계용 이벤트 생성은 원자적으로 처리하며, 외부 메시지 전송 같은 부수 효과는 트랜잭션 재시도 함수 밖에서 멱등 처리한다. Firestore 트랜잭션은 경쟁 시 재실행되고 오프라인에서는 실패할 수 있다. [공식 트랜잭션 설명](https://firebase.google.com/docs/firestore/manage-data/transactions).
- 수락 트랜잭션과 `CLOSING` 상태 전이가 같은 권위 있는 세션 문서를 읽어 충돌하도록 설계한다. 직렬화 순서상 결과가 먼저 확정되면 한 번 포함하고, 종료가 먼저 확정되면 거부한다. 클라이언트 타임스탬프나 네트워크 전송 시작 시간으로 소급하지 않는다. 서버 commit 시각으로 사후 감사하며 초 단위의 정밀한 마감이나 도착 순서의 공정성을 약속하지 않는다. 정확한 마감·재시도·고부하 락/경합 동작은 실제 에뮬레이터 및 별도 부하 시험 전 미검증이다.
- 서버가 받은 클라이언트 점수·응답은 변경 가능한 주장이다. 범위·중복·정답 산식 등을 검증해도 이동·과일·몬스터·시간을 완전히 입증할 수 없다. 결과를 `client_reported`/검증 수준과 함께 표시하고 정식 랭킹이나 부정행위 방지 보장으로 표현하지 않는다. 검증 가능한 서버 권위 실행/재생이 필요하다면 별도 설계·승인이 필요하다.
