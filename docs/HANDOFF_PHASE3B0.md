기준 `c5c63c3f281185565ff7e6ad53898c30ec8dd81e`. Phase 3A 설계 PASS를 바탕으로 작성한 **개발 전 계약 및 시험 모델**이다. 900초는 HOJA 2.0의 확정 제품 요구사항이며 5~30분 범위·비례 전환·팀 평균·60초 예고·재실행은 교사/감독 승인 전 권장안이다. 이 단계에서 실제 싱글 엔진·600초 trace·기존 점수·QR·운영 Firebase/GAS/Sheets·main을 바꾸지 않았다.

## 방 시간 설정 계약

- 방 생성 시 15:00 기본, `−1분`·`+1분`은 60초 단위, 현재 시간을 크게 표시. 기본값 복귀는 검토 항목. 교사만 DRAFT/LOBBY에서 변경하며 RUNNING 시작 시 같은 설정을 전 참가자에 고정한다.
- 검증 후보 범위 300~1800초(5~30분), 정수·60초 배수. 이 범위는 **가안**이다. 클라이언트 값은 신뢰하지 않고 서버가 검증하며 서버 계산 결과와 `settingsRevision`을 세션에 보관한다. 시작 후 수정 거부. 재접속 시 고정 설정을 다시 전달한다.
- 서버 계약 필드: `durationSeconds`, `sunsetThresholdSeconds`, `nightThresholdSeconds`, `questionGuideThresholdSeconds`, `settingsRevision`. 권장 계산은 석양 `round(durationSeconds*2/9)`, 밤과 방향 안내 `round(durationSeconds/9)` 초. 900초→200/100/100, 600초→133/67/67. 1초 단위 반올림과 비례 방식은 가안이며 정해진 범위와 반올림 경계·한 프레임에서 여러 경계 통과도 추후 시험한다.
- 현재 FINISH 시간 보너스는 `round(ceil(remainingMs/1000) * found / 25)`다. 길게 설정한 방은 남은 시간이 늘어 보너스가 커질 수 있다. 예: 발견 25개이고 남은 시간이 600초/900초라면 보너스는 각각 600/900점이다. 이 분석은 점수 산식 변경 제안이 아니다. 방 시간 간 점수 비교와 공식 랭킹 자격은 별도 결정 전 금지/미확정이다. 25문항 조기 종료에서 어떤 보너스를 줄지도 미결정이다.

| RUNNING | 종료 예고 | RUNNING | 교사; 권장 60초, 미제출·연결 상태 안내. 자동 마감 시간은 미확정 |

각 성공 상태·데이터 변경은 서버 `revision` 단조 증가, 수신 측은 이전 revision 무시. 재시도된 동일 명령의 revision 증가 정책은 구현 전에 명시해야 한다. 학생은 팀·시간·교사 역할·상태·점수/집계 직접 쓰기 불가; 자신의 참가·실행 상태와 허가된 팀 집계만 읽는다. 교사는 자신의 세션만 관리하고 개별 응답 접근·개인정보 범위는 학교 정책과 승인에 따른다. Rules는 기본 거부이며 신뢰 서버에도 역할·소유권 검증을 적용한다. 사용자·UID 문자열을 비교하는 로컬 모델은 실제 인증이 아니다.

## 자료 및 메시지 계약

| 식별자/필드 | 권위와 역할 |
| --- | --- |
| `sessionId` | 서버 발급 임의 식별자. 공개만으로 권한을 부여하지 않음 |
| `participantId` | 세션 내 서버 발급; 인증 UID와 멤버십으로 결합. 동명이인 UID를 자동 병합하지 않음 |
| `runId` | 참가자와 세션에 귀속된 서버 발급 실행. 재실행은 이전 실행 무효화 후 새 ID |
| `connectionEpoch` | 같은 탭 복구 때 증가. 이전 epoch의 **신규** 요청은 거부 |
| `requestId` | 클라이언트가 최초 제출 전에 만들고 재시도에 고정. 충돌 범위는 `(sessionId,participantId,runId,requestId)` |
| `revision`, `settingsRevision` | 각각 세션 변화와 설정 변화의 서버 단조 증가 값 |
| `gameVersion`, `cartridgeIds`, `cartridgeVersions` | 시작 전 서버 고정·입장 시 일치 검증. 실제 콘텐츠 해시·순서 규약은 추후 계약 확정 |
| `result` | 종료 이유·기존 점수 구성·문항 수·정답·과일·남은 시간·검증 수준. 클라이언트 보고이며 서버가 실플레이를 입증한 데이터가 아님 |

제안 저장 경로는 `sessions/{sessionId}`, 그 아래 `participants/{participantId}`, `runs/{runId}`, `teams/{teamId}`, 인증·소유권으로 제한한 비공개 응답/감사 로그다. 공개 집계와 개인 응답은 분리하며 저장 기간·삭제 정책은 미결정이다. 새 class 메시지는 타입·버전·세션·참가자·실행 ID를 명시하고 source/origin 검증을 하며 기존 싱글 bridge는 유지한다. QR 입장 자격의 만료·재발급·복제 및 로그 노출 방지는 구현 전 별도 확정한다.

## 제출·마감·재접속

1. 신뢰 서비스가 인증·세션/참가자/실행 소유권을 먼저 확인한다. 이전에 수락된 동일 요청 ID와 동일한 정규화 payload는 세션이 CLOSING/FINALIZED이거나 epoch가 바뀌어도 기존 영수증을 반환한다. 인증 상실·권한 철회된 사용자에게 영수증을 무조건 공개한다는 뜻은 아니다.
2. 같은 요청 ID에 다른 내용은 충돌. 다른 요청 ID로 같은 실행을 제출해도 한 번만 집계한다. 새로운 결과는 RUNNING·현재 epoch·활성 run·고정 버전을 만족해야 수락한다. 응답이 유실되면 동일 ID·동일 본문으로 재시도한다.
3. 결과 수락과 CLOSING은 같은 서버 권위의 세션 상태를 트랜잭션에서 확인해 직렬화한다. 제출이 먼저 커밋되면 한 번 수락; 종료가 먼저 커밋되면 신규 제출 거부. 클라이언트 송신 시각으로 늦은 결과를 소급하지 않는다. 실제 DB 원자성·오프라인·경합은 별도 에뮬레이터/부하 시험이 필요하다.
4. 원래 탭이 살아 있는 통신 단절은 동일 참가자·run을 유지하고 연결 세대를 갱신한다. 새로고침·종료·기기 교체는 현재 Scene 복원 미지원으로 자동 복원하지 않는다. 교사 승인 재실행은 이전 run의 집계 기여를 무효화하고 새 run과 감사 기록을 발급한다. 과거 영수증은 과거 수락 사실이며 현재 집계 유효 여부와 별도다. 제외도 감사하고 시작 시 확정된 분모를 임의 수정하지 않는 안이다.
5. 방이 마감돼도 개인 게임 타이머를 0으로 만들지 않는다. 제출 불가 안내 및 남은 게임의 처리 UX는 추후 구현한다. 마감 전 예고·네트워크 지연과 예외 재개방은 제품 승인 전 가안이다.

팀 비교는 `확정된 팀원의 수`를 분모로 합계를 나눈 평균을 권장한다. 미제출·포기·제외·재실행을 별도 표시하며 미제출자를 정상 완주로 표기하지 않는다. 모의 모델은 미제출/제외 기여를 0으로 계산하지만 이는 **가안**이며 교사 최종 승인이 필요하다. 동점은 공동 순위. 학생별 활동 점수는 `client_reported`로 명시하고 공식 공개 랭킹이나 완전한 위조 방지로 취급하지 않는다.

## 동일 난이도 조사

지상 생성은 `js/world/surface-generator.js`의 시드 PRNG, 동굴은 `js/world/cave-variation.js`의 시드 경로를 사용한다. 새 run의 시드 자체는 `arcade.html`에서 `Math.random()`으로 뽑는다. `js/parent-gameplay.js`는 오답·보기·문항 집합을 `Math.random()`으로 섞고, `js/quiz-normalizer.js`도 RNG를 받아 기본적으로 `Math.random`을 쓴다. 이외 게임 효과 등도 전역 난수를 쓴다. 따라서 같은 지형 시드만으로 문제·보기·전체 게임 결과가 같아지지 않는다. 동일 맵 구성과 동일 독립 출제 단위(UQ) 집합을 고정하고 순서는 달리하는 안을 검토하되, UQ 매핑·승인된 데이터·예외 및 실제 재현 시험 전까지 보장하지 않는다. 기존 문제 추출/문제은행을 수정하지 않았다.

## Firebase 격리 및 설치 조사

`verification/phase3a/emulator/`의 `demo-hoja-phase3a` 시험 지침·loopback 설정과 deny-all Rules를 보존한다. 새 모의 테스트는 실행 중 Firebase를 호출하지 않는다. 선택 프로젝트 검증, 두 emulator 존재·loopback 주소 검증, 허용 외 대상 차단과 싱글 Firebase 비초기화를 모의했지만 **실제 네트워크 차단이나 Rules 검증은 아니다**.

이 기기의 Node는 24.21.0이며 `firebase` CLI와 Java 런타임은 찾지 못했다. Firestore 에뮬레이터 JAR 하나와 npm 캐시 항목은 있으나 CLI/Java 실행 가능성을 입증하지 않는다. 사용자 영역의 별도 npm prefix에 Firebase CLI를 설치하고 별도 JDK를 `JAVA_HOME`으로 지정하거나, 별도 컨테이너/CI에서 설치할 수 있다. 현재 `docker`, `podman`, `brew` 명령도 발견되지 않았다. 최신 요구 버전은 설치 시 다시 확인해야 한다. 공식 문서: [Firebase CLI](https://firebase.google.com/docs/cli/), [에뮬레이터 설치](https://firebase.google.com/docs/emulator-suite/install_and_configure), [demo 프로젝트 격리](https://firebase.google.com/docs/emulator-suite/connect_firestore). SDK별 대상 검증·외부 요청 차단·서버 SDK의 Rules 우회 대응도 별도 구현·검증해야 한다. CLI 설치, 인증, 실제 Rules 또는 동시성 시험은 수행하지 않았다.
